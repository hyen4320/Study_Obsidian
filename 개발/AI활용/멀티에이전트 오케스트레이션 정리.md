# 멀티에이전트 오케스트레이션 정리

> 공부용 정리 · 2026-09-07
> 결론부터: **오케스트레이터는 "일을 쪼개고 나눠주고 합치는 하나의 메인 세션"이고, 서브에이전트는 "각자 빈 컨텍스트에서 자기 일만 하고 요약만 돌려주는 일회용 작업자"입니다.** 개발팀 비유는 절반만 맞습니다. 팀원끼리 대화하지 못하고, 매번 새로 태어나며, 결과는 오직 오케스트레이터에게 텍스트 한 덩어리로만 돌아옵니다.

---

## 1. 왜 이 구조가 필요한가

단일 세션의 한계가 세 가지입니다.

| 한계 | 증상 | 멀티에이전트가 푸는 방식 |
| --- | --- | --- |
| **컨텍스트 한도** | 파일 100개 읽으면 대화창이 꽉 차서 앞 내용을 잊음 | 서브에이전트가 100개를 읽고 **요약 20줄만** 반환. 오케스트레이터 창은 20줄만 소모 |
| **직렬 처리** | 프론트 조사 → 백엔드 조사 → 문서 작성 순서로 대기 | 독립적인 일은 **동시에** 여러 에이전트에 던짐 |
| **역할 혼선** | "보안 관점으로 봐" + "성능 관점으로 봐"를 한 번에 시키면 뭉개짐 | 관점마다 **다른 시스템 프롬프트**를 가진 에이전트를 따로 띄움 |

핵심 자원은 시간이 아니라 **컨텍스트 윈도우**입니다. 멀티에이전트는 병렬화 기법이기 이전에 **컨텍스트 절약 기법**입니다.

---

## 2. 개념 정리

### 2-1. 오케스트레이터 (Orchestrator)

사용자와 대화하는 **메인 세션 그 자체**입니다. 별도 프로그램이 아닙니다.

하는 일 네 가지:

1. **분해(Decompose)** — 요청을 독립적으로 끝낼 수 있는 단위로 쪼갬
2. **위임(Dispatch)** — 각 단위에 맞는 에이전트를 골라 프롬프트를 만들어 던짐
3. **수집(Collect)** — 반환된 요약들을 받음
4. **병합(Synthesize)** — 모순을 조정하고 최종 산출물로 합침

오케스트레이터가 직접 코드를 짜기 시작하면 컨텍스트가 오염되어 병합 능력을 잃습니다. **오케스트레이터는 가급적 읽고 쓰지 않고 나눠주기만 해야 합니다.**

### 2-2. 서브에이전트 (Sub-agent)

독립된 컨텍스트 윈도우를 가진 **일회용 LLM 인스턴스**입니다.

구성 요소:

- **시스템 프롬프트** — 이 에이전트의 역할·규칙 (예: "너는 FastAPI 백엔드 리뷰어다. 수정하지 말고 지적만 해라")
- **도구 허용 목록** — 읽기만 시킬지, 쓰기까지 허용할지 (예: Explore 계열은 Write 금지)
- **모델 지정** — 조사는 저렴한 모델, 설계는 상위 모델

성질:

- **격리** — 오케스트레이터의 대화 내용을 모름. 프롬프트에 넣어준 것만 앎
- **일회성** — 끝나면 컨텍스트가 사라짐. 다음 호출은 완전히 새 인스턴스
- **단방향** — 서브에이전트끼리 직접 대화 불가. 반드시 오케스트레이터를 경유
- **텍스트 반환** — 마지막 메시지 한 덩어리만 결과로 올라옴

### 2-3. 워크플로 (Workflow) — 오케스트레이션의 상위 개념

오케스트레이터가 "판단으로" 나눠주는 게 아니라, **스크립트로 순서를 못 박아두는** 방식입니다.

| 구분 | 동적 오케스트레이션 | 워크플로(스크립트) |
| --- | --- | --- |
| 순서 결정 | 오케스트레이터가 그때그때 판단 | 코드에 고정 |
| 재현성 | 매번 다를 수 있음 | 동일 입력 → 동일 경로 |
| 적합 | 탐색적 작업, 요구 불명확 | 반복 작업(리뷰 파이프라인, 보고서 생성) |

## 3. 동작 원리 — 한 번의 사이클

```
[사용자] "프론트 미구현 목록을 백엔드 API 기준으로 검증해줘"
    │
    ▼
[오케스트레이터]  ← 여기만 사용자와 대화함
    │  1) 분해: (A) 프론트 화면 목록 수집  (B) 백엔드 API 목록 수집
    │           (C) 대조 및 판정  ← A,B 결과가 있어야 가능
    │
    ├──▶ [에이전트 A: frontend-explorer]  빈 컨텍스트
    │        app/ 순회 → 화면 42개 확인 → "요약 30줄" 반환
    │                                              │
    ├──▶ [에이전트 B: backend-explorer]   빈 컨텍스트   │ 동시 실행
    │        app/engine 순회 → 엔드포인트 61개 → "요약 25줄" 반환
    │                                              │
    │◀─────────────── 요약만 올라옴 (원본 파일 내용은 안 올라옴) ─┘
    │
    │  2) 병합: A요약 + B요약을 프롬프트에 넣어 C 실행
    ├──▶ [에이전트 C: matcher]  A,B 요약을 입력으로 받음
    │        대조 → "미연결 12건" 반환
    ▼
[오케스트레이터] 최종 답변 작성 + md 파일 기록
```

**여기서 반드시 이해할 두 가지**

1. **A와 B는 서로의 존재를 모릅니다.** 병렬 실행은 "의존성이 없을 때만" 가능합니다. C는 A·B에 의존하므로 반드시 뒤에 옵니다. 의존성 그래프를 그려서 같은 층은 동시에, 다른 층은 순차로 — 이게 오케스트레이션의 전부입니다.
2. **A가 읽은 파일 원문은 오케스트레이터에 올라오지 않습니다.** 요약이 부실하면 오케스트레이터는 그 사실조차 모릅니다. 그래서 **반환 형식을 프롬프트에서 강제**해야 합니다("파일 경로·줄번호·판정을 표로 반환").

## 4. 팀 비유가 깨지는 지점 (가장 중요)

| 사람 개발팀 | 멀티에이전트 | 실무 대응 |
| --- | --- | --- |
| 옆자리에 물어봄 | 에이전트 간 대화 불가 | 필요한 정보는 오케스트레이터가 프롬프트에 **복사해서** 넣어야 함 |
| 어제 한 일을 기억 | 매 호출마다 기억 상실 | 상태는 **파일(md)에 기록**해서 다음 에이전트가 읽게 함 |
| 모르면 되물음 | 되묻지 못하고 **추측해서 진행** | 프롬프트에 "모르면 추측 말고 '불명'으로 반환" 명시 |
| 중복 작업 회피 | 3개 에이전트가 같은 파일을 3번 읽음 | 담당 범위를 **경로 단위로 배타 분할** |

에이전트 수를 늘리면 비용은 선형으로 늘지만 품질은 그렇지 않습니다. **에이전트 5개짜리 구성이 2개짜리보다 나쁜 경우가 흔합니다** — 요약 손실이 누적되기 때문입니다.

## 5. 실제 구성 방법

### 5-1. 서브에이전트 정의 파일

`.claude/agents/<이름>.md` (프로젝트 단위) 또는 `~/.claude/agents/<이름>.md` (전역)에 둡니다.

```markdown
---
name: backend-reviewer
description: FastAPI 백엔드 코드를 읽고 문제를 지적한다. 코드는 수정하지 않는다.
tools: Read, Grep, Glob
model: sonnet
---

너는 seohwa 백엔드 리뷰어다.

## 범위
- C:\work\seohwa\backend/app 하위만 본다. frontend는 절대 열지 않는다.

## 규칙
- 파일을 수정하지 않는다. 지적만 한다.
- 추측하지 않는다. 근거 파일과 줄번호를 반드시 붙인다.
- 확인 불가한 항목은 "불명"으로 표시한다.

## 반환 형식 (반드시 이 표만 반환)
| 파일:줄 | 문제 | 심각도 | 근거 |
```

- `description`이 **에이전트 선택 기준**입니다. 오케스트레이터는 이 한 줄만 보고 어느 에이전트에 맡길지 정합니다. 애매하면 엉뚱한 에이전트가 뽑힙니다.
- `tools`를 좁히는 것이 안전장치입니다. 조사용 에이전트에 Write를 주면 시키지 않은 파일을 만듭니다.

### 5-2. 이 프로젝트에 맞는 최소 구성 (오늘 할 일 기준)

업무일지의 "멀티에이전트 구축 — 프론트/백엔드/사무작업"에 대응하면 이렇게 됩니다.

| 에이전트 | 역할 | 도구 | 반환물 |
| --- | --- | --- | --- |
| `backend-dev` | FastAPI 구현·수정 | Read, Edit, Write, Bash | 변경 파일 목록 + 요약 |
| `frontend-dev` | Next.js 화면 구현 | Read, Edit, Write, Bash | 변경 파일 목록 + 요약 |
| `repo-explorer` | 조사 전용(읽기만) | Read, Grep, Glob | 근거 표 |
| `doc-writer` | 보고서·요구사항·일정 md | Read, Write | md 초안 |
| `verifier` | 결과 검증(다른 에이전트 산출물 재확인) | Read, Grep, Bash | 합격/불합격 + 사유 |

`verifier`를 반드시 두는 이유: 서브에이전트는 **"했다"고 보고하고 안 한 경우**가 있습니다. 오케스트레이터는 요약만 받으므로 스스로 검증할 수 없습니다. 검증은 별도 에이전트가 원본을 다시 읽어야 합니다.

### 5-3. 오케스트레이션 프롬프트 예시

```
너는 오케스트레이터다. 직접 코드를 읽거나 쓰지 마라.

1. 요청을 독립 작업으로 쪼개고 의존성 그래프를 먼저 출력해라.
2. 의존성이 없는 작업은 한 번에 동시 호출해라.
3. 각 서브에이전트에는 필요한 컨텍스트를 프롬프트에 직접 넣어라
   (에이전트는 이 대화를 볼 수 없다).
4. 모든 구현 작업 뒤에는 verifier를 반드시 붙여라.
5. 마지막에 결과를 병합해 하나의 md로 남겨라.
```

## 6. 실패 패턴과 처방

| 증상 | 원인 | 처방 |
| --- | --- | --- |
| 결과가 뭉뚱그려짐 | 반환 형식 미지정 | 프롬프트에 표 스키마 강제 |
| 같은 일을 두 번 함 | 담당 범위 겹침 | 경로 단위 배타 분할 |
| "완료했습니다"인데 안 됨 | 검증 부재 | verifier 에이전트 필수 |
| 비용만 나가고 느림 | 의존 작업을 병렬로 착각 | 의존성 그래프를 먼저 출력시키기 |
| 엉뚱한 에이전트가 뽑힘 | description이 모호 | "언제 쓰는지"를 한 문장으로 명확히 |
| 맥락을 잃음 | 세션 간 기억 없음 | 상태를 md 파일로 남기고 다음 호출에 경로를 알려줌 |

---

## 7. 한 줄 요약

**오케스트레이터 = 컨텍스트 관리자, 서브에이전트 = 컨텍스트 소각장.** 더러운 일(대량 읽기, 시행착오)은 서브에이전트가 자기 컨텍스트에서 태우고 깨끗한 요약만 올려보내며, 오케스트레이터는 그 요약들로 판단만 합니다.

---

## 미확인 사항

- 실제 구축하신 `~/.claude/agents/` 설정 파일은 접근 권한이 없어 확인하지 못했습니다. 폴더를 연결해 주시면 실제 에이전트 정의별로 역할·도구 범위·중복 여부를 대조해 이 노트에 덧붙이겠습니다.
