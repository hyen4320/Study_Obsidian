# 멀티에이전트 오케스트레이션 구성 v2 (토큰 절약 버전)

작성일: 2026-09-11 · 대상: `C:\work\seohwa-agents` · 상태: **설계 확정, 미반영** (반영 지시 시 적용)

## 결론

v1의 "전부 Fable" 구조를 **판단은 Fable, 구현은 Opus, 정해진 명령·잡일은 Haiku** 세 층으로 나눈다. 기존 9개 역할의 모델을 재배분하고(수정 9개), 잡일용 Haiku 서브에이전트 8개(프론트 3 · 백엔드 3 · 문서 2)와 어려운 작업 전담 Fable 서브에이전트 3개(프론트 · 백엔드 · 문서 각 1)를 새로 만든다(신규 11개). 예상 절감은 비용 기준 50~65%, 잡일 위임으로 상위 에이전트 컨텍스트가 줄어드는 효과까지 합치면 최대 70% 수준이다. 핵심 변경 지점은 `agent-run.sh` · `fleet-orch.sh`의 `--model` 추가, `wt-new.sh`의 `settings.local.json` `model` 키, 그리고 각 worktree의 `.claude/agents/` 서브에이전트 정의다.

## 2. 동작 흐름

### 2.1 프론트·백엔드 개발

```
판단(Fable, 메인)
  ├─ 1. fe-explore(Haiku): 대상 파일·심볼·사용처 목록 ← 결과 요약만 컨텍스트에 들어옴
  ├─ 2. DEV-FE(Opus): "이 파일의 이 함수를 이렇게, 완료 판정은 verify 통과" 명세로 구현
  ├─ 3. fe-verify(Haiku): tsc/lint/i18n/verify 실행 → 실패 항목만 보고
  │     └─ 실패 시 2번으로 (최대 LOOP_MAX_TRIES)
  ├─ 4. (2회 이상 실패 또는 구조 판단 필요) fe-hard(Fable): 원인 분석·수정 방향 → 결과를 DEV-FE에 전달
  └─ 5. fe-summarize(Haiku): diff 요약·커밋 메시지·완료 보고 초안 → review-req
```

핵심은 Opus 개발 에이전트가 **탐색과 검증 로그 읽기를 직접 하지 않는 것**이다. 파일 위치는 explore가, 실패 항목은 verify가 추려서 넘기므로 개발 에이전트 컨텍스트가 작게 유지되고, 상위 모델은 요약만 본다.

### 2.2 문서작업

```
판단(Fable, 메인)
  ├─ 1. doc-find(Haiku): 볼트·입력 자료·증빙에서 관련 부분 발췌
  ├─ 2. OFFICE(Opus 1M): 발췌 자료 + 템플릿으로 초안 작성·수정·삭제
  ├─ 3. doc-check(Haiku): 형식·필수 절·표기·기밀 검사 → 지적 목록
  ├─ 4. doc-judge(Fable): 구성·증빙 대응·심사 기준 검토 → 수정 지시
  │     └─ 지시를 OFFICE(Opus 1M)가 반영 → 3·4 반복
  └─ 5. verify.sh → review-req → 발행
```

Fable은 **읽고 판단만** 하고 긴 출력을 내지 않으므로 비용이 억제되고, 실제 쓰기는 전부 Opus 1M이 한다.

### 2.3 구조상 제약

Claude Code에서 서브에이전트는 다른 서브에이전트를 호출할 수 없다. 따라서 "DEV-FE가 fe-explore를 부르는" 구조가 아니라 **메인(판단) 세션이 explore → DEV → verify 순으로 호출**한다. 헤드리스 루프에서는 `agent-run.sh`의 프롬프트에 "탐색은 fe-explore, 검증은 fe-verify 서브에이전트에 위임하십시오"를 명시하면 DEV 세션이 메인 역할을 겸해 서브에이전트를 부른다(DEV 세션 자체가 최상위 세션이므로 가능).

## 3. 반영 방법 (파일별 변경 내역)

### 3.1 `scripts/agent-run.sh` — 레인별 `--model`

```bash
case "$LANE" in
  fe|be)  MODEL="opus" ;;
  office) MODEL="opus[1m]" ;;
esac
[[ "$ROLE" == reviewer ]] && MODEL="opus"
( cd "$CWD" && timeout "$TIMEOUT" "$CLAUDE" -p "$P" --model "$MODEL" --permission-mode bypassPermissions )
```

### 3.2 `scripts/fleet-orch.sh` — 판단은 Fable 고정

```bash
"$CLAUDE" -p "$P" --model "claude-fable-5-1" --permission-mode bypassPermissions
```

Fable은 `opus` `sonnet` `haiku`처럼 짧은 별칭이 없으므로 전체 모델 ID를 쓴다(실제 ID는 `claude --model` 도움말 또는 `/model`에서 확인).

### 3.3 `scripts/wt-new.sh` — `settings.local.json`에 `model` 키

worktree 생성 시 레인에 따라 `"model": "opus"` 또는 `"model": "opus[1m]"`을 넣어 대화형 탭 세션도 같은 모델로 뜨게 한다.

### 3.4 `.fleet/config.env` — 모델을 설정값으로

```
MODEL_ORCH=claude-fable-5-1
MODEL_DEV=opus
MODEL_OFFICE=opus[1m]
MODEL_DESIGN=opus[1m]
MODEL_REVIEW=opus
MODEL_HELPER=haiku
MODEL_HARD=claude-fable-5-1
MAX_WT_BE=3          # 기존 2 → 3 (운영 실태에 맞춤, 2026-09-11 확정)
```

스크립트는 이 값을 읽는다. 모델을 바꿀 때 스크립트를 고치지 않아도 된다. 백엔드 동시 상한은 worktree당 컨테이너 2개가 뜨므로 3이면 컨테이너 6개 · 포트 8101~8103 / 5433~5435가 동시에 쓰인다.

### 3.5 서브에이전트 정의 — `roles/agents/` 템플릿 + `wt-new.sh`가 복사

`roles/agents/fe/` `be/` `office/` 아래에 1.2절의 md 파일을 두고, `wt-new.sh`가 레인에 맞는 것을 `<worktree>/.claude/agents/`로 복사한다. 형식 예:

```markdown
---
name: fe-verify
description: tsc·lint·i18n·verify.sh를 실행하고 실패 항목만 파일:행으로 요약합니다. 코드를 고치지 않습니다. 구현 후·커밋 전에 호출하십시오.
model: haiku
tools: Bash, Read
---
결론부터 보고합니다. 통과/실패 한 줄 → 실패 항목(파일:행 · 메시지) 목록. 통과한 항목·전체 로그는 싣지 않습니다.
```

```markdown
---
name: fe-hard
description: 원인 불명 버그, 여러 파일에 걸친 리팩터링, 구조 판단 전담. Opus 개발 에이전트가 2회 이상 실패했거나 ADR급 판단이 필요할 때만 호출하십시오. 일반 구현에는 쓰지 않습니다.
model: claude-fable-5-1
tools: Read, Grep, Glob, Bash
---
원인과 수정 방향을 두괄식으로 냅니다. 직접 구현하지 않고 "어느 파일을 어떻게"까지만 지정합니다.
```

`description`의 호출 조건이 절감의 핵심이다. 조건이 없으면 메인 세션이 안전하게 가려고 Fable을 자주 불러 절감 효과가 사라진다.

### 3.6 역할 파일(`roles/dev-fe.md` `dev-be.md` `office.md`) — 위임 규칙 추가

3절 작업 규율에 다음을 추가한다. "파일·심볼 탐색은 `*-explore`(문서는 `doc-find`)에, 검증 실행과 로그 읽기는 `*-verify`(문서는 `doc-check`)에, diff·로그 요약은 `*-summarize`에 위임합니다. 직접 grep·전체 로그 읽기를 하지 않습니다. 같은 오류로 두 번 막히면 `*-hard`에 원인 분석을 요청합니다."

### 3.7 `~/.claude/agents/` 기존 서브에이전트

`fleet-reviewer`에 `model: opus`, `fleet-qa` `fleet-integrator`에 `model: sonnet`을 추가한다(권장, 지시 범위 밖).

## 4-1. v1 대비 결과물 품질 차이 판단

결론: **최종 산출물 품질은 거의 같고(체감 차이 5% 이내), 대신 "한 번에 끝나는 비율"이 낮아져 재시도가 늘어난다.** 품질을 지키는 장치는 모델이 아니라 이미 갖춰진 verify → 리뷰어 판정 → 통합 게이트이며, v2에서도 이 게이트는 그대로다.

| 산출물 | 품질 차이 | 근거 |
| --- | --- | --- |
| 카드 범위가 명확한 fe/be 기능 구현 | 거의 없음 | 명세가 정해진 구현은 Opus와 Fable 결과가 수렴. verify(tsc·lint·i18n·pytest)와 리뷰어가 같은 기준으로 거른다 |
| 여러 파일에 걸친 변경·원인 불명 버그 | v1이 우세, 단 `*-hard`(Fable)로 보완 | Opus는 1차 시도 성공률이 낮아 `LOOP_MAX_TRIES` 소진 빈도가 오른다. 2회 실패 시 Fable이 원인을 잡아주므로 최종 결과는 회복된다 |
| RF(리팩토링, 동작 변경 0건) | 소폭 저하 가능 | "동작을 안 바꾸면서 구조만 바꾸는" 판단은 상위 모델이 강하다. RF 카드는 `*-hard`를 처음부터 쓰거나 리뷰어를 Fable로 두는 것을 권장 |
| 설계 규율 준수(확장 지점·의존 방향·3파일 이내) | 소폭 저하 가능 | Opus는 "돌아가게" 우회하는 경향이 상대적으로 강해 `changes-requested`가 늘 수 있다. 리뷰어 설계 판정이 잡아내므로 통합 결과에는 반영되지 않는다 |
| 문서작업(보고서·제안서) | 거의 없음, 구성 판단은 유지 | 작성은 Opus 1M, 구성·증빙 대응·심사 기준 판단은 `doc-judge`(Fable)가 그대로 하므로 v1과 같은 판단 수준이 유지된다 |
| 디자인(와이어프레임) | 없음 | 저충실도·기존 토큰 추출만 하는 작업이라 모델 차이가 드러나지 않는다 |
| 카드 작성·의존성·ADR 승인 | 없음 | 판단은 Fable 그대로 |

품질이 아니라 **속도·재시도**에서 차이가 난다. 카드당 개발 재기동 횟수가 v1 대비 1.3~1.5배로 늘 수 있고, 그만큼 카드 완료까지의 벽시계 시간이 길어진다. 다만 재시도 비용은 Opus+Haiku 단가이므로 비용 절감 폭(50~65%) 안에서 흡수된다.

품질이 실제로 떨어지는 경우는 세 가지다. ① `*-hard` description의 호출 조건이 너무 엄격해 Fable이 필요한데도 안 불리는 경우, ② Opus 개발 에이전트가 탐색을 위임하지 않고 직접 grep해 컨텍스트가 커져 후반부 판단이 흐려지는 경우, ③ 리뷰어까지 하위 모델로 내려 게이트가 약해지는 경우. ③은 v2에서 리뷰어를 Opus 이상으로 두어 막고, ①②는 반영 후 `.fleet/logs/`의 재시도 횟수와 `changes-requested` 비율을 v1 기간과 비교해 조정한다.

## 4-2. 품질 유지의 조건 — "Fable이 필요할 때 반드시 불린다"

결론: **v2의 품질은 Fable을 아끼는 데서가 아니라, Fable이 필요한 순간에 빠짐없이 불리는 데서 결정된다.** 이 조건만 지켜지면 v1과 산출물 품질 차이는 없다. 따라서 Fable 호출을 "판단에 맡기는 것"이 아니라 아래처럼 **규칙으로 고정**한다.

### 호출 조건 (하나라도 해당하면 Fable)

| 트리거 | 호출 대상 | 호출 주체 | 판정 방법 |
| --- | --- | --- | --- |
| 같은 카드에서 verify 실패 또는 `changes-requested` **2회 누적** | `fe-hard` / `be-hard` | `fleet-loop.sh` (자동) | `status_get <ID> tries` ≥ 2 |

| 오류 원인을 Opus 가 "불명" 으로 보고 | `*-hard` 즉시 | DEV 세션 (규칙) | 보고 문구 |

### 호출을 보장하는 장치

- **description 에 조건을 양쪽으로 쓴다.** "…일 때만 호출" 뿐 아니라 "…이면 반드시 호출" 을 함께 적는다. 한쪽만 쓰면 메인 세션이 아끼는 쪽으로 기울어 필요한 순간에 안 부른다.
- **루프가 강제한다.** 위 표의 "자동" 항목은 `fleet-loop.sh` 와 `agent-run.sh` 가 조건을 보고 프롬프트에 "`*-hard` 로 원인 분석 후 진행하십시오" 를 박아 넣는다. 에이전트의 판단에 맡기지 않는다.
- **역할 파일에 의무로 적는다.** `dev-fe.md` `dev-be.md` `office.md` 3절에 "같은 오류로 두 번 막히면 `*-hard`" · "초안이 나오면 `doc-judge`" 를 규칙으로 넣는다.
- **호출 여부를 기록한다.** 서브에이전트 호출은 `.fleet/logs/<ID>/` 에 남으므로, 카드 완료 보고에 "`*-hard` 호출 n회 · `doc-judge` 호출 n회" 를 적게 하고 리뷰어가 트리거 조건 대비 누락을 확인한다.

### 반대 방향 — 과다 호출 방지

Fable 이 너무 자주 불리면 절감이 사라진다. 허용 기준은 **카드당 `*-hard` 1~2회 · `doc-judge` 2~3회**이고, 주간으로 `.fleet/report/` 에서 호출 비율을 본다. 카드의 30% 이상에서 `*-hard` 가 불리면 Opus 구현 명세가 모호한 것이므로 카드·explore 보고의 상세도를 올리는 쪽으로 고친다(Fable 을 더 부르는 쪽이 아니라).

## 5. 주의점

- **Opus 1M은 절감 수단이 아니다.** 20만 토큰을 넘는 컨텍스트는 단가가 올라간다. 문서·디자인처럼 긴 자료가 필수인 곳에만 쓴다.
- 서브에이전트 본문 지침은 짧게 유지한다. 호출마다 붙는 토큰이다.
- Haiku 잡일 에이전트에는 Write·Edit를 주지 않는다. 결과를 "요약"으로만 돌려주는 것이 역할이다.
- 역할이 겹치는 서브에이전트를 늘리지 않는다. 메인 세션의 선택 혼란과 관리 비용만 는다.
- 반영 후 첫 1~2일은 `.fleet/report/`의 카드당 소요 시간·재시도 횟수를 v1과 비교해 Opus 구현 품질이 유지되는지 확인한다.
