- 메인스레드


메인스레드가 1번으로 떠오르지 않는 이유
- 대부분의 화면에서 실제 문제가 되는 일이 드물기 때문.

메인스레드가 문제가 되는 상황
- 실시간으로 데이터가 쏟아지는 상황
- 스크롤과 애니메이션과 입력이 뒤엉키는 인터랙션 많은 화면

메인스레드 문제의 결과
- 스크롤이 뚝뚝 끊기기
- 버튼 반응이 늦음
- 검색창 글자 늦게 반응
- 사용자의 경험을 저해하는 결과를 초래함

개발자의 사고
버벅임 발생->코드의 알고리즘, 불필요한 연산 찾기
이는 원인이 될 수도 있지만 대부분의 경우 *코드가 느려서가 아닌 그 코드를 메인스레드가 붙잡고 있기 때문*

브라우저에서 메인스레드의 역할
메인스레드는 코드로 건드릴 수 있는 거으 대부분은 메인스레드에 몰려있음
연산, 렌더링, 이벤트 처리, 네트워크 응답 처리, 프레임워크의 내부 동작


메인스레드가 하는 일
- 자바스크립트 실행
	- 작성한 코드
	- 이벤트 핸들러
	- 타이머
	- 네트워크 응답 콜백
	- 프레임워크 내부 동작
- 화면 그리기
	- DOM이나 스타일이 바뀌어 화면을 갱신할 일이 생길 때 아래와 같은 순서를 거친다.
	- requestAnimationFrame 콜백 실행 - 프레임을 그리기 직전에 실행하기로 등록해둔 자바스크립트
	- 스타일 계산 - 각 요소에 적용될 최종 CSS값 계산
	- 레이아웃 - 각 요소의 위치와 크기를 계산(리플로우라고도 불림)
	- 페인트 - 무엇을 어떤 색으로 그릴지 페인트 명령을 만듬
바뀐 것이 없으면 이 단계들을 통째로 건너뜀. 매 프레임 반드시 도는 것이 아님. 합성 단계만 컴포지트 스레드로 넘어감. 화면을 그리는 파이프라인 대부분은 메인스레드 몫이다.

문제
여기서 문제는 두종류의 일이 같은 스레드에서 한 줄로 선다는 것. 자바스크립트는 단일 스레드 이벤트 루프 모델로 설계됨. 메인 스레드는 한 번에 하나의 작업만 처리하고 그 작업이 실행되는 동안 다른 어떤 것도 할 수 없음.

자바스크립트 함수 하나가 200밀리초 동안 돌고 있으면 200밀리초 동안 브라우저는 화면을 다시 그리거나 사용자의 클릭을 받지 못함. 보통 50밀리초를 넘기면 문제로 간주

메인스레드를 오래 붙잡는 것은 화면을 멈추는 것과 같음. 이런 점은 웹 성능 지표와도 연결됨
웹 성능 지표인 INP와 TBT와 같은 지표들에 영향을 줌
INT(Interaction to Next Paint): 사용자가 무언가를 눌렀을 때 화면이 반응하기까지의 시간을 잼
TBT(Total Blocking Time):페이지 로딩 중 메인 스레드가 막혀 있던 총 시간
이 두 지표는 메인 스레드가 얼마나 오래 막혀있었는지 표현하는 것에 가까움
성능최적화란 상당 부분이 하나의 스레드를 어떻게 아껴 쓰느냐의 문제임

문제의 해결은 두 방법이 있음. 하나는 메인 스레드 안에서 시간을 잘 나눠 쓰는 것 다른 하나는 아예 일을 메인 스레드 밖으로 내보내는 것


비싼 자원을 아껴쓰기
첫번째 방법 중 시간을 영리하게 쓰는 방법
- 너무 긴 작업을 어떻게 잘게 나눌 것인가
- 너무 잦은 작업을 어떻게 묶을 것인가
- 여러 작업 중 무엇을 먼저 할 것인가
- 지금 꼭 안해도 되는 작업을 어떻게 미룰 것인가

각각 쪼개기, 모으기, 우선순위, 미루기라고 부를 것임. 앞의 둘은 태스크 크기를 다듬는 일 뒤의 둘은 실행의 시기를 정하는 일. 이 중 쪼개기가 나머지의 기반이 됨. 테스크에 경계가 생겨야 비로소 그 사이에 무엇을 먼저 넣고 무엇을 뒤로 보낼지도 정할 수 있다.

쪼개기
라이브 스트리밍 방송의 채팅창을 기준으로 생각하면 초당 수백개씩 쏟아지는 채팅은 하나씩 얌전히 도착하지 않음. 트래픽이 몰리면 서버가 수십 개씩 뭉텅이로 보내기도 함. 방에 입장하는 순간에 밀린 채팅 수백 개가 한꺼번에 내려오기도 함. 이 덩어리를 받은 즉시 한 호흡에 전부 그린다면 채팅 하나 그릴 때마다 DOM 생성과 스타일 계산, 레이아웃, 페인트가 따라 붙음. 그 수백 번이 하나의 태스크 안에서 연속으로 실행된다. 그동안 사용자가 자기 채팅을 입력하려 해도 입력창은 버벅이고 화면의 다른 애니메이션도 끊긴다. 쏟아지는 남의 채팅이 메인 스레드를 독차지하여 내 입력을 방해함.

해법은 큰 덩어리를 작은 조각으로 나누고 조각과 조각 사이에서 메인 스레드에 잠깐씩 제어권을 돌려주면됨. 그 틈에 브라우저는 밀려 있던 화면 갱신과 입력 처리를 해낼 수 있다.

똑같은 스트리밍 채팅이라도 20개를 그릴 때마다 메인 스레드를 잠깐 놓아주면 그 사이에 밀려있는 입력과 프레임생산을 할 수 있다. 하지만 오해하면 안되는 것이. 양보가 일을 빠르게 만들어주지는 않는다. 총 작업량은 그대로이며 오히려 양보를 위해 몇 밀리초씩 기다리는 오버헤드가 생기므로 실제로는 더 오래 걸린다.  입력 뿐아니라 렌더링까지 살아나는데 메인스레드는 태스크가 실행되는 동안 아무것도 할 수 없다.프레임을 만드는 렌더링 파이프라인도 태스크 중간에 끼지 못하고 태스크와 태스크 사이에만 실행될 수 있음. 양보란 태스크와 태스크 사이를 만들어주는 것이고 틈이 적당히 있어야 프레임을 자주 만들 수 있다. 프레임을 자주 만들면 화면이 부드러워 보이고 이는 사용자의 경험이 좋아지고 성능이 개선된 느낌을 준다.
