### 1.3 확장점
- 비표준 포트: `redef Modbus_Extended::additional_tcp_ports += { 12345/tcp };` (`testing/analyzer/custom_port.zeek` 가 이 동작을 검증 — 미설정 시 `modbus.log` 가 생기지 않아야 하고, `likely_server_ports` 만 추가해도 파싱되지 않아야 함).
- 새 기능 코드 상세화: record 추가 → `Log::ID` 추가 → `zeek_init` 에 `Log::create_stream` → 이벤트 핸들러 작성 → `handled_modbus_funct_list`(`main.zeek:237-277`)에 이름 추가(미추가 시 `modbus_message` 가 헤더만 기록, 1823-1842).
- 출력 필터링: 스트림별 `Log::PolicyHook`.
- 값 사전 교체: `&redef` 상수.
- 한계: 프로토콜 파싱 자체(벤더 전용 기능 코드 등)는 이 패키지 밖(Zeek 코어)이라 여기서 확장 불가. README "vendor/product specific functions are not included".

### 1.4 로그 데이터 모델
`Modbus_Detailed`(`main.zeek:29-48`): `ts`, `uid`(Zeek 연결 ID), `id`(conn_id: orig_h/orig_p/resp_h/resp_p), `tid`(트랜잭션 ID), `unit`(유닛 ID), `func`(기능 이름 문자열), `address`(시작 주소), `quantity`, `request_values`/`response_values`(`vector of count`), `modbus_detailed_link_id`, `matched`(bool), `request_subfunction_code`/`response_subfunction_code`, `request_data`/`response_data`, `exception_code`, `mei_type`.

- **요청-응답 상관**: 요청 핸들러는 같은 `tid` 의 응답이 이미 있으면 합쳐 기록하고 없으면 `modbus_requests[c$id][tid]` 에 보관(`main.zeek:317-339`), 응답 핸들러는 그 반대(`350-386`). 결과적으로 **요청+응답 한 쌍 = 1레코드**, `matched=T`. 순서가 뒤바뀐 경우(응답 먼저)도 처리한다.
- **미매칭 처리**: `connection_state_remove`(1881-1897)에서 남은 항목을 `matched=F` 로 기록. 단, 이 핸들러는 종료된 연결만이 아니라 **전체 테이블을 순회하고 `delete modbus_requests; delete modbus_responses;` 로 전역 삭제**한다. 즉 어떤 연결이든 하나가 닫히면 다른 연결의 대기 항목도 미매칭으로 방출된다(코드상 사실, 의도 여부는 미확인).
- **예외**: `modbus_exception`(1847-1879)이 대기 요청에 `exception_code` 를 붙여 기록, 요청이 없으면 예외만 단독 기록.
- **하위 로그 연결**: `generate_uid()`(219-233, 16자 난수)로 만든 `modbus_detailed_link_id` 가 상세 로그와 mask-write / read-write-multiple / device-identification 로그를 잇는다.
- **방향 표현**: 하위 3개 로그는 `is_orig` + `source_h/p`, `destination_h/p` + `request_response`("REQUEST"/"RESPONSE")를 따로 둔다 — `id` 는 연결 기준, source/destination 은 패킷 기준.
- **자산 식별**: `Read_Device_Identification`(106-127) — `conformity_level`, `device_id_code`, `object_id`(VendorName/ProductCode/MajorMinorVersion/…, `main.zeek:146-155`), `object_value`. 응답의 오브젝트마다 1행(1671-1684).
- 선언만 있고 쓰이지 않는 것: `modbus_pending`(`main.zeek:49`, grep 결과 참조 1건).
- 타임스탬프: `network_time()`(패킷 시각). 정규화 스키마(ECS)는 **사용하지 않음** — Zeek TSV/JSON 고유 스키마.
- `redef DPD::ignore_violations += { Analyzer::ANALYZER_MODBUS }`(`main.zeek:134`) — 프로토콜 위반이 나도 분석기를 떼지 않는다.

### 1.5 네트워크 모델 / 1.6 자체 보안
- 해당 없음(라이브러리 성격). 수집 지점은 Zeek 를 어디에 붙이느냐의 문제. README 는 포트 직접 등록 시 페이로드 검증 없이 분석기로 보내므로 "Modbus 전용 포트만 설정"하라고 경고한다.

### 1.7 암시하는 요구사항
- 요청과 응답을 트랜잭션 ID 로 묶은 **단일 레코드**가 분석 단위여야 한다(쓰기 값과 결과를 한 줄에서 봄) — `main.zeek:317-386`.
- 매칭 실패도 버리지 않고 `matched=F` 로 남긴다(무응답 요청·요청 없는 응답 자체가 이상 징후) — `main.zeek:1881-1897`.
- 대기 상태는 연결 단위로 한정·만료되어야 한다(현재 구현은 전역 삭제) — 같은 위치.
- 코드→이름 사전은 미지값 기본값을 갖고 운영자가 교체 가능해야 한다 — `consts.zeek:21`.
- 비표준 포트는 설정으로 추가하되 오탐 위험을 문서화 — `main.zeek:24, 283-286`, README.
- 파서 버전에 따라 로그 수준이 달라지므로 **커버리지 표**를 유지 — README "Coverage"(19개 중 15개 상세).
- PCAP + 기준 로그 회귀 테스트 — `testing/traces/`, `testing/baseline/`.

## 2. icsnpp-dnp3

### 2.1 구조와 흐름
- `scripts/consts.zeek`(270줄), `scripts/main.zeek`(271줄). `zkg.meta`: `zeek >=3.0.0`.
- 흐름: Zeek 내장 DNP3 분석기 이벤트(`dnp3_application_request_header`, `dnp3_application_response_header`, `dnp3_object_prefix`, `dnp3_object_header`, `dnp3_crob`, `dnp3_pcb`) → 연결 객체에 임시 상태 저장 → `dnp3_control.log`, `dnp3_objects.log`.

### 2.2 핵심 추상화
| 이름 | 위치 | 내용 |
|---|---|---|
| `Log::ID` 확장 | `scripts/main.zeek:14-15` | `LOG_CONTROL`, `LOG_OBJECTS` |
| `Control` record | `main.zeek:20-39` | 제어 블록 로그 |
| `Objects` record | `main.zeek:45-59` | 오브젝트 헤더 로그 |
| 연결 상태 확장 | `main.zeek:63-66` | `redef record connection += { dnp3_control, dnp3_objects }` — 헤더 이벤트에서 채운 값을 뒤 이벤트가 이어받음 |
| 스트림 생성 | `main.zeek:71-79` | `PolicyHook` 없음(modbus 와 차이) |
| 상수 | `consts.zeek:17`(function_codes), `:63`(trip code), `:72`(operation type), `:83`(status codes), `:104`(dnp3_objects) | 모두 `&redef`, 미지값은 `unknown-%x` 또는 `unknown`(266) |

핸들러: `dnp3_object_prefix`(84), 요청 헤더(97), 응답 헤더(112), `dnp3_crob`(128, 기록 169), `dnp3_pcb`(175, 기록 216), `dnp3_object_header`(222, 기록 270). 우선순위로 실행 순서를 제어한다(헤더 `&priority=2`, 기록 핸들러 `&priority=-4`).

### 2.3 확장점
- 새 오브젝트 그룹/바리에이션 이름: `dnp3_objects` 테이블 redef. 테이블에 없는 타입은 `"unknown"` 이 되어 **기록하지 않는다**(`main.zeek:233-234`).
- 새 로그 종류: record + `Log::ID` + 핸들러 추가.

### 2.4 데이터 모델
- `Control`: `ts`, `uid`, `id`, `is_orig`, `source_h/p`, `destination_h/p`, `block_type`("Control Relay Output Block"/"Pattern Control Block"), `function_code`(SELECT/OPERATE/RESPONSE 등), `index_number`(포인트 인덱스), `trip_control_code`(Nul/Close/Trip), `operation_type`(Pulse On/Off, Latch On/Off), `clear_bit`, `execute_count`, `on_time`, `off_time`, `status_code`.
  - 제어 코드 1바이트를 비트 분해: `(control_code & 0xc0)/64` → trip, `& 0xf` → operation, `& 0x20` → clear (`main.zeek:156-158`).
  - `status_code` 는 `function_code == "RESPONSE"` 일 때만 채우고 아니면 삭제(163-167).
- `Objects`: `function_code`(READ 또는 RESPONSE), `object_type`, `object_count`, `range_low`, `range_high`. 요청 방향은 READ 가 아니면, 응답 방향은 RESPONSE 가 아니면 기록하지 않음(254-255, 263-264). 수량/범위는 응답에서만 채움.
- **요청-응답 상관 ID 없음**: 요청과 응답이 별도 행이며 `uid` + 시간 + `index_number` 로 추정해야 한다(baseline `dnp3_control.log` 에서 SELECT → RESPONSE → OPERATE 가 연속 행으로 확인됨).
- DNP3 링크 계층 주소(마스터/아웃스테이션 주소), 포인트 **값**: 이 확장 로그에는 없음(Zeek 기본 `dnp3.log` 쪽 내용은 미확인).
- ECS 미사용.

### 2.7 암시하는 요구사항
- **제어 명령은 읽기와 별도 로그**로, 대상 포인트·동작·결과 상태까지 구조화 — `main.zeek:20-39`.
- Select-Before-Operate 순서 추적이 가능하도록 function_code 를 행마다 남김 — `main.zeek:97-123`.
- 로그량 통제: 관심 기능(READ/RESPONSE)·알려진 오브젝트만 기록 — `main.zeek:233-264`.

### 3.7 암시하는 요구사항

## 4. conpot

조사 범위: `conpot/core/`, `conpot/protocols/__init__.py`·`schemas.py`·`modbus/`·`dnp3/`(일부)·`s7comm/`(일부)·`proxy/`, `conpot/templates/`(default, plc_modbus, proxy), `conpot/emulators/plc/`, `conpot/cli.py`, `conpot/utils/server_tasks.py`, `Dockerfile`, `docker-compose.yml`, `AGENTS.md`. 나머지 프로토콜 구현 상세, VFS(`core/filesystem.py`), `tools/conpot_cloner.py`, hpfeeds 전송 암호화는 **미확인**. 이 버전은 XML 이 아니라 **TOML 템플릿 + asyncio** 구조다(과제 설명의 "템플릿 XML"과 다름).

### 4.1 구조와 데이터 흐름
```
cli.main()  ─ 설정(.cfg) + 템플릿 디렉터리 해석
  └ _async_main()
      ├ Databus.initialize(template.toml)         # 장치 상태(키-값)
      ├ VFS 초기화
      └ start_services()
          ├ collect_protocols(): name_mapping × <protocol>.toml → 스키마 검증 → 서버 인스턴스
          ├ LogWorker (asyncio.Queue 소비자)
          └ collect_proxies(): proxy.toml
공격자 ──▶ 프로토콜 서버.handle() ──▶ get_session() → AttackSession.log_event()
                                        └ normalize_event() → log_queue ─▶ LogWorker._dispatch()
                                                                         ├ HPFriends ├ SQLite ├ Syslog └ JSON
```
근거: `conpot/cli.py:87-158`(`_async_main`), `161-287`(`main`); `conpot/core/protocol_startup.py:67-92, 160-211`; `conpot/core/log_worker.py:102-133`.

### 8.3 보안 요구사항

**모니터링 스택 자체**
- S-01. 모든 사용자 접근은 단일 인증 프록시를 거치고, 인증 방식(로컬·LDAP·OIDC)을 선택할 수 있다. [Malcolm — `config/auth-common.env.example:1-2`, `nginx/nginx.conf`(각 location 의 `nginx_auth_rt.conf`)]
- S-02. 역할 기반 접근 제어로 조회·쓰기·PCAP 열람·파일 다운로드·업로드·자산 편집 권한을 분리한다. RBAC 이 꺼진 모드에서는 모든 사용자가 관리자임을 명시한다. [Malcolm — `auth-common.env.example:32-35` 및 `ROLE_*` 정의]
- S-03. 출하 기본 자격증명을 두지 않고 설치 시 생성한다(난수 비밀, 해시 저장). [Malcolm — `scripts/control.py:2120-2131, 2377, 2774-2810`. 반례: GRFICSv2 `README.md:85-90`, labshock compose `:241`, conpot `testing.cfg:34-35`]
- S-04. 비밀은 설정과 분리된 파일에 두고 권한 600, 저장소 제외, 읽기 전용 마운트로 필요한 구성요소에만 준다. [Malcolm — `.gitignore`(auth-related 절), `control.py:1463-1468, 2371`, `logstash-start.sh:117-119`, `docker-compose.yml:44-52`]
- S-05. 센서 → 집계기 전송은 상호 TLS 로 인증한다. 양쪽 모두 상대 인증서를 검증해야 한다. [Malcolm — `logstash/pipelines/input/01_beats_input.conf:6-10`. 주의: `filebeat/filebeat-logs.yml:251` 은 `verification_mode: none`. 반례: labshock syslog UDP, conpot `loggers/syslog.py:34-39`]
- S-06. 외부 노출면을 최소화한다 — 공개 포트는 인증 프록시 하나, 나머지는 루프백. [Malcolm — `docker-compose.yml:209, 288, 1052, 1460-1461`. 반례: labshock 17개 포트 전체 인터페이스 공개]
- S-07. 저장소·UI·내부 서비스 간에도 TLS 와 인증을 적용하고 인증서 검증을 켠다. [Malcolm — `opensearch.env.example:11`(https). 기본값 `OPENSEARCH_SSL_CERTIFICATE_VERIFICATION=false`(:23)와 `nginx.conf:179, 213, 354` 의 `proxy_ssl_verify off` 는 검증 생략. 반례: labshock `xpack.security.enabled=false`(`:258`)]
- S-08. 구성요소는 비특권 사용자로 실행하고, 필요한 커널 권한만 사유와 함께 부여한다. [Malcolm — `config/process.env.example`(PUID/PGID), `docker-compose.yml:29-33, 565-570`; conpot — `cli.py:48-84, 213-234`, `Dockerfile:50`. 반례: labshock `privileged: true`(`:127`), Docker 소켓 마운트(`:57`)]
- S-09. 신뢰 경계를 문서화한다 — 내부망이 단일 신뢰 영역인지, 수집(업로드)이 신뢰 작업인지. [Malcolm — `docs/contributing-security-model.md`(문서)]
- S-10. 서버 버전 등 불필요한 정보 노출을 막는다. [Malcolm — `nginx/nginx_security_headers.conf`]
- S-11. 수집 데이터 속 민감정보(평문 암호 등) 기록 여부를 제어한다. [Malcolm — `zeek/config/local.zeek:11`(`ZEEK_DISABLE_LOG_PASSWORDS`), `malcolm_severity.yaml:27`("Cleartext password")]

**패시브 센서**
- S-12. 센서는 수신 전용이어야 하며 감시 대상 망으로 송신하지 않는다. 미러 인터페이스에는 관리 트래픽을 섞지 않는다. [labshock — mirror_network 분리 모델(`:46-50, 128-132`); Malcolm — `PCAP_IFACE_TWEAK` 주석(캡처 전용/관리 겸용 구분, `pcap-capture.env.example:12-15`). 송신 차단을 강제하는 코드는 **미확인**]
- S-13. 포트만으로 분석기를 강제 연결하면 무관한 트래픽이 오분류되므로 전용 포트에만 적용한다. [icsnpp-modbus — README 포트 설정 절, `testing/analyzer/custom_port.zeek`]

**허니팟**
- S-14. 인증 없는 원격 입력의 모든 읽기 경로에 길이 상한과 타임아웃을 두고, 한 연결이 다른 서비스를 멈추지 못하게 한다. [conpot — `protocols/modbus/modbus_server.py:27, 87, 148-202`, `utils/asyncio_serve.py:79`]

- S-18. 허니팟의 외부 호출(공인 IP 조회, 피드 전송)은 끌 수 있어야 한다. [conpot — `testing.cfg:30-40`, `cli.py:114-116`]

**테스트베드**
- S-19. 의도적 취약점과 기본 계정을 가진 구성요소는 격리망 전용임을 강제하고, 외부 경로를 기본 차단한다. [GRFICSv2 — host-only 어댑터(`README.md:59-61`), 취약 libmodbus(`:23`); labshock — entrypoint Disclaimer. 주의: labshock 은 `ip route del default` 가 주석 처리되어 기본 경로가 남는다(`router/entrypoint.sh:9-10`)]
