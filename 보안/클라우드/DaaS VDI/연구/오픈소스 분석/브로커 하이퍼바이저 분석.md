### 1.2 엔드투엔드 흐름 (코드 근거)

1. 로그인 — `U/web/util/authentication.py:55` `check_login()`
   - 인증기 조회(비활성 제외) → 실패 횟수 캐시 키 `authenticator.id + username`(:75), IP별 카운터 → 한도 초과 시 "Temporarily blocked"(:88).
   - `U/core/auths/auth.py:271` `authenticate()`: 루트 사용자는 신뢰 출발지에서만(:292), 인증기 `is_ip_allowed`(:304), `auth_instance.authenticate(...)`, 유효 그룹이 하나도 없으면 로그인 거부(:327).
   - 성공 시 `request.session.cycle_key()`(`authentication.py:111`), `log_login`(`auth.py:512`).
2. 풀 조회 — `U/web/util/services.py:122` `get_services_info_dict()`
   - 사용자 그룹 → `ServicePool.get_pools_for_groups()`(`U/models/service_pool.py:567`): 그룹 할당 + 그룹 ACTIVE + 풀 상태 + visible + (USABLE publication 존재 또는 publication 불필요 서비스).
   - 전송 필터 `_is_valid_transport`(:161): 출발지 IP 허용 + 전송 타입의 OS 지원 + 전송 인스턴스의 OS 허용.
3. 데스크톱 할당 — `U/web/util/services.py:457` `enable_service()` → `UserServiceManager.get_user_service_info()`(`U/core/managers/userservice.py:975`) → `locate_user_service(create=True)`(:926) → `get_assignation_for_user()`(:593)
   - 기존 할당 재사용(서비스가 `spawns_new` 가 아니면) → 풀 restrained/생성 불가 검사 → L1 캐시에서 `state=USABLE, os_state=USABLE` → 다음 `state=USABLE` → 다음 `state=PREPARING` 순으로 `select_for_update` + 조건부 `update(user=..., cache_level=0) == 1` 로 원자적 선점 → 없으면 `max_srvs` 검사 후 `create_assigned_for()`(:208) 로 신규 생성.
   - CACHE_HIT / CACHE_MISS 이벤트 기록.
4. 전송 선택 — `get_user_service_info()` 내부: 전송 미지정 시 풀의 전송을 priority 순으로 훑어 IP·OS 조건에 맞는 첫 번째 선택, 지정 시 그 전송이 풀에 속하는지와 IP 허용을 재검증. 유지보수 모드·캘린더 접근 거부 검사 포함.
5. 접속 티켓 — `enable_service()`: 무작위 scrambler(32자)로 웹 비밀번호를 대칭 암호화해 `TicketStore.create(data)` 에 넣고(`U/models/ticket_store.py:101`, 기본 유효 60초) `udss://` 형태 링크 반환. `own_link` 전송(HTML5 등)은 별도 URL.
   - 네이티브 클라이언트가 `U/REST/methods/client.py:121` `process()` 로 티켓 교환: 티켓 조회(무효화 보류) → 사용자·서비스 재검증 → `transport.get_transport_script(...)` → 준비 중이면 `TicketStore.revalidate`(:214) 로 재시도 허용, 그 외에는 `finally` 에서 `TicketStore.invalidate`(:226).
   - 전송 스크립트는 서명 포함(`U/core/transports/transport.py:245-268`, `.mldsa65.sig` 파일, `SignatureAlgorithm.MLDSA65` — `U/core/types/transports.py:92-93`), KEM 키가 오면 응답을 암호화(`as_encrypted_dict`, `types/transports.py:144`).
6. 터널 — 터널형 전송이 `TicketStore.create_for_tunnel()`(`ticket_store.py:248`) 로 티켓 발급(예: `U/transports/RDP/rdptunnel.py:95-98`, 유효기간 = 시작 대기시간 + 60초). 터널 서버는 `U/REST/methods/tunnel_ticket.py:53` `TunnelTicket.post()` 로 `start`/`stop` 통지.
7. 게스트 에이전트(actor) — `U/REST/methods/actor_v3.py`: `Register`(:315) → `Initialize`(:419) → `Ready`(:641)/`IpChange`(:633) → `Login`(:695) → `Logout`(:763), 그 외 `Log`(:812), `Ticket`(:838), `Unmanaged`(:992), `Notify`(:1080).
8. 로그아웃 회수 — `Logout.process_logout()`(`actor_v3.py:771`) → `OSManager.logged_out()`(`U/core/osmanagers/osmanager.py:321`) → OS 매니저의 `is_removable_on_logout()` 이 참이면 `UserServiceManager.release_from_logout()`(`userservice.py:540`): 캐시 복귀 허용 + L1 캐시 여유 필요 시 캐시로 되돌림, 아니면 `release()`(REMOVABLE 표시).
9. 삭제 — `UserServiceRemover` 워커(`U/workers/userservice_cleaner.py:72`)가 REMOVABLE 을 집어 `UserServiceManager.remove()`(`userservice.py:498`) → 플러그인 `destroy()` → `UserServiceOpChecker` 가 완료까지 폴링.

## 3. OpenUDS — 확장점 (무엇을 구현하면 되는가)

### 3.1 새 하이퍼바이저/플랫폼
1. `U/services/<Name>/` 패키지 생성, `ServiceProvider` 서브클래스: 접속 정보 GUI 필드(호스트·포트·사용자·`gui.PasswordField`), `offers`, 동시 생성/삭제 한도 필드, `test()`.

4. 기존 머신 배정형이면 `FixedService`/`FixedUserService`.
5. 필요 시 `jobs.Job` 서브클래스로 플랫폼 전용 정리 잡.
6. `__init__.py` 에서 클래스를 임포트하면 재시작 시 자동 등록(`U/services/__init__.py` 주석과 `initialize()`).

### 3.2 새 프로토콜 전송
`Transport` 서브클래스: `PROTOCOL`, `group`, `supported_oss`, `own_link`; 네이티브 클라이언트형은 `get_transport_script()`(서명된 스크립트 + 파라미터), 브라우저형은 `get_link()`; 대상 포트 도달 검사 `is_ip_allowed()`; 터널형은 `TicketStore.create_for_tunnel()` 로 티켓 발급. 서비스 쪽 `allowed_protocols` 와 맞아야 풀에 붙는다(`is_protocol_supported`, `transport.py:151`).

### 3.4 그 외
`OSManager`(게스트 OS 설정·로그아웃 정책), `MFA`(2차 인증 수단), `Notifier`(알림 채널), `Job`(주기 작업) 모두 같은 `Module`/팩토리 방식.

## 6. 보안 추상화

### 6.1 접속 티켓 (OpenUDS)
- `TicketStore`(`U/models/ticket_store.py:61`): `owner`(:68), `validity`(:70, 기본 60초 — `U/core/consts/ticket.py` 의 `DEFAULT_TICKET_VALIDITY_TIME`), 최대 1주(`MAX_TICKET_VALIDITY_TIME`), 티켓 길이 48(`TICKET_LENGTH`).
- 일회성: `get(..., invalidate=True)` 가 삭제 건수로 선점 확인, 0 이면 "Already consumed"(:174-176) — 동시 읽기 경쟁 방지.
- 만료: `stamp + validity < now` 면 거부(:161).
- secure 티켓: 데이터는 owner 에서 PBKDF2 로 유도한 키로 AES-CBC 암호화하고 DB 의 owner 는 고정 문자열로 바꿔 저장 — 키가 DB 에 남지 않음(:94-98, :121-129). 터널 티켓은 `uuid + owner(8자)` 를 이어 붙인 값이라 티켓 자체가 복호화 키 역할(:257, :278-288).
- 사용자 비밀번호는 티켓에 평문으로 넣지 않고 일회용 scrambler 로 암호화하며 scrambler 는 링크로만 전달(`web/util/services.py` `enable_service`).
- 주의점(코드에 드러난 것): 티켓 본문 직렬화에 pickle 사용(:169, `# nosec` 주석), `settings.DEBUG` 이면 클라이언트 티켓을 무효화하지 않음(`client.py:224-226`).

### 6.2 터널 인증
- 터널 서버 → 브로커: `Authorization: Bearer sk-<token>`, 토큰은 `Server.token_hash` 와 대조(`U/REST/authentication.py:167-171`, 해시는 SHA-256 — `U/models/servers.py:419`), 서버 종류별 구분 `ServerType`(`U/core/types/servers.py:49-54`: TUNNEL/ACTOR/SERVER/UNMANAGED).
- 추가로 신뢰 출발지 검사(`tunnel_ticket.py:85`), 토큰 없으면 거부(:91).
- `start`: `once` 표시가 있으면 즉시 무효화(:131), 세션 종료 통지용 티켓을 새로 발급(:146, 유효 `MAX_SESSION_LENGTH` = 2주), 응답은 터널이 보낸 KEM 공개키로 암호화(:158). `stop`: 송수신 바이트·지속 시간 기록(:106-118).
- 터널 등록은 ADMIN 역할(`TunnelRegister.ROLE`, :176).
- 터널 서버 쪽 계약: `UT/crates/server/src/broker/mod.rs:65` `trait BrokerApi { start_connection; stop_connection }`, 설정 `UT/udstunnel.conf:7-9`(`ticket_api_url`, `dangerous_disable_ssl_verify=false`, `broker_auth_token`). 터널 서버 내부(세션·스트림·UDP)는 읽지 않음 — 미확인.

### 6.3 actor ↔ broker 인증
- 등록: `Register`(`actor_v3.py:315`)는 STAFF 역할 필요(:331), 서버 토큰을 생성해 해시만 저장(:374, :389), 등록자·IP 기록(:381-382).

- Ready: 브로커가 머신 IP 용 자체 서명 인증서를 만들어 내려주고 저장(:596, :616-618), 에이전트가 낸 `secret` 으로 통신 URL 구성(:174-175). 브로커 → 에이전트 호출은 저장된 인증서로 핀닝, 인증서가 없으면 요청 자체를 거부(`U/core/managers/userservice_helpers/comms.py:78-95`).

- 에이전트 쪽 계약: `UA/crates/shared/src/broker/api/mod.rs:47` `trait BrokerApi`(register, initialize, ready, unmanaged_ready, login, logout, log, test), OS 추상 `UA/crates/shared/src/system.rs:118` `trait System`(rename_computer, join_domain, change_user_password 등).

## 7. 비기능 측면

### 7.1 OpenUDS
- 비동기 작업: 플러그인 메서드는 즉시 `TaskState` 반환, `UserServiceOpChecker`(`U/core/managers/userservice_helpers/opchecker.py:220`)가 `suggested_delay` 간격으로 `check_state()` 재호출(`check_later`:283). 상태별 처리기 `UpdateFromPreparing/Removing/Canceling/Valid/Other`(:117-:206). 작업 실행 중 상태가 바뀌었으면 해당 체크 폐기(:302-305). UserService 당 지연 작업 1개 보장(`make_unique`:234).
- 재시도: `RetryableError` → `retry_later()`(`dynamic/userservice.py:288-289`, :325), 최대 재시도 `USRV_MAX_RETRIES`(= 1일 분량), 한 상태 최대 체크 `USRV_MAX_STATE_CHECKS`(= 2시간 분량) — `U/core/consts/services.py`. Publication 도 동일 구조(`PUB_*`).

## 9. 프로젝트를 가로지르는 공통 패턴과 차이

### 공통 패턴
1. 템플릿 → 클론 모델: OpenUDS publication(Proxmox 는 클론 후 템플릿화), oVirt 풀(템플릿 버전 변경 감지 `templateVersionChanged`), Proxmox `template` + linked clone. 세 프로젝트 모두 "원본을 직접 쓰지 않고 읽기 전용 기준 이미지에서 파생" 한다.
2. 비영구 데스크톱의 원상 복구: OpenUDS 는 삭제 후 재생성 또는 스냅샷 복구 후 캐시 복귀, oVirt 는 stateless 스냅샷 복원, Proxmox 는 스냅샷 rollback 프리미티브 제공.
3. 사전 준비 풀: OpenUDS L1/L2 캐시, oVirt `prestartedVms` — 둘 다 주기 모니터가 부족분을 배치 단위로 채우고 동시 기동 수를 제한한다.
4. 콘솔 접속은 단명 일회성 비밀: oVirt 120초 OTP, Proxmox SPICE 30초 만료, OpenUDS 60초 티켓. 모두 발급 시점에 권한을 검사하고 발급을 감사 로그에 남긴다(oVirt·OpenUDS 확인, Proxmox 감사 기록은 미확인).
5. 장기 작업의 비동기화와 식별자: OpenUDS TaskState 폴링, oVirt 명령 콜백, Proxmox UPID 워커.
6. 동시성 제어: OpenUDS DB 행 잠금, oVirt 엔진 잠금(`USER_VM_POOL`, VM 잠금), Proxmox 설정 파일 잠금 + `lock` 키.
7. 사용자 포털 권한과 관리자 권한의 분리: OpenUDS Role + 객체 권한, oVirt ActionGroup 의 user/admin 구분과 필터 조회, Proxmox 경로별 권한.

### 차이
- 계층: OpenUDS 는 하이퍼바이저 위의 브로커(플랫폼 다중화·전송·인증기·에이전트를 모두 플러그인화). oVirt 는 관리 평면 안에 풀 기능을 내장(단일 플랫폼). Proxmox 는 풀 할당 개념이 없고 프리미티브(클론·템플릿·스냅샷·콘솔 티켓·권한)만 제공.
- 할당의 표현: OpenUDS 는 `UserService.user` 외래키, oVirt 는 VM 에 대한 권한 행, Proxmox 는 해당 없음.
- 영구성: OpenUDS 는 OS 매니저의 로그아웃 정책 3종, oVirt 는 풀의 `stateful` 플래그 + AUTOMATIC/MANUAL 타입.
- 게스트 에이전트: OpenUDS actor 는 브로커와 직접 통신(토큰·인증서), Proxmox 는 호스트의 QEMU 게스트 에이전트 채널을 API 로 감싸고 세분 권한 부여, oVirt 게스트 에이전트는 이번 범위에서 미확인(`VmLogon` 액션 존재만 확인).
- 접속 경로: OpenUDS 만 자체 터널과 전송 스크립트 서명·암호화 계층을 가짐. oVirt·Proxmox 는 SPICE/VNC 프록시 수준.
- 감사: OpenUDS 는 해시 체인 + 외부 타임스탬프 앵커까지 구현. oVirt 는 `AuditLogType` 이벤트. Proxmox 는 작업 로그(UPID)/syslog 호출 확인, 그 이상은 미확인.

## 11. 미확인 항목 정리
- OpenUDS: 테넌트 개념의 별도 엔티티 유무, 브로커 다중 노드의 세션 공유/리더 선출 방식, 하이퍼바이저 API 명시적 rate limiter, `ENFORCE_ZERO_TRUST` 의 동작, `backoff.py` 사용처, 터널 서버·actor 의 Rust 내부 구현(트레이트 시그니처와 설정 파일만 확인), Proxmox 외 플랫폼 플러그인(oVirt/OpenStack/Xen 등)의 세부 로직(클래스 선언과 oVirt 콘솔 티켓 호출만 확인), 암호화 키의 외부 KMS 연동.
- oVirt: 사용자 포털 프런트엔드와 REST API 계층, SSO/세션 토큰, 게스트 에이전트 연동(`VmLogon` 세부), `AddVmPool` 의 VM 생성 절차, 쿼터 세부.
- Proxmox: 역할(Role) 정의·ACL 전파·API 토큰 권한 분리·VNC/인증 티켓의 수명과 서명(`PVE::AccessControl`, pve-access-control 저장소가 클론에 없음), 콘솔 접근의 감사 기록 방식.
